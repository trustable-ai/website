# 13 — One generator: absorb index.py, publish the catalog and images from trustable.it

Today the site is built by two scripts across two repositories, and everything
the browser loads points at `raw.githubusercontent.com`:

- **`support/index.py`** — a submodule of `trustable-ai/.github`, checked out
  under `support/`. It talks to the GitHub API with `gh`, and writes
  `support/index.json`, published at
  `https://raw.githubusercontent.com/trustable-ai/.github/refs/heads/main/index.json`.
- **`generator.py`** — reads that file, clones each application repo for its
  README, and writes the Zola sections under `content/apps/`.
- **Every screenshot is hotlinked.** spec/12-readme.md deliberately dropped the
  local copy under `static/apps/` in favour of the catalog's raw URL, so both
  `extra.icon` and every relative image in a README resolve to GitHub.

Two costs follow. The build straddles a submodule boundary, with a publishing
order that has to be remembered by hand (spec/7-publish.md: push the catalog
*first*, or `main`'s submodule pointer names a commit GitHub does not have).
And the published site is not self-contained: a page cannot render without
GitHub, images carry GitHub's availability rather than ours, and a repository
going private breaks the gallery silently.

This spec collapses the two scripts into one and serves both the catalog and
every image from `trustable.it`. After it, `generator.py` is the only thing
that talks to the GitHub API, the `support` submodule is no longer part of
building the site, and nothing the browser loads points at GitHub.

## What does not change

- **`support/index.py` stays where it is, untouched**, and keeps publishing the
  upstream `index.json` from `trustable-ai/.github`. That file is what
  **Trustable itself** reads for discovery (spec/8-index.md), which is a
  separate consumer with a separate release cycle. This spec stops the *website*
  from depending on it; it does not retire it.
- The catalog rules of spec/8-index.md are the specification of the logic being
  moved: the `Trustable:` marker, `<key>=<value>` parameters, `templates=`
  being required to be a starter, the `<name>-templates` convention and its
  fallback, `_index.md` parsing, grouping by the first `# ` heading, and the
  sort order. Behaviour is preserved exactly; only its home changes.
- `templates/page.html` and `templates/starter-cards.html` need no change: both
  already emit `extra.icon` through `| safe`, so a site-absolute path works.

## Plan

### 1. Absorb `support/index.py` into `generator.py`

Port the catalog logic into `generator.py` as a first stage that runs before
generation. The functions come across essentially as they are — this is a move,
not a rewrite — with the changes noted below.

**Ported unchanged** (same names, same behaviour, see spec/8-index.md):

- `normalize_templates()`, `parse_description()`, `parse_applications()` and
  their module-level regexes (`KEY_VALUE`, `REPO_SEGMENT`, `APPLICATION_LINE`,
  `GROUP_HEADING`), plus the constants `ORG`, `MARKER` (renamed, see below),
  `APPLICATION_INDEX`, `APPLICATION_SCREENSHOT`, `REPO_BASE`,
  `TEMPLATES_SUFFIX`.
- `fetch_repositories()` — `gh api --paginate orgs/<ORG>/repos`, with the
  defensive multi-array decode it already carries.
- `build_starters()` — the whole starter/application classification, including
  the stderr notes for a repository with no `templates=`, a missing `_index.md`,
  and a listing with no `# ` heading.
- `fetch_raw()` — still needed to read each `_index.md`, but through `gh`
  rather than raw.githubusercontent.com (see below), so it becomes
  `fetch_file(repo, path)`.

**Changed on the way in:**

- **`MARKER` collides.** `index.py` uses it for the `trustable:` description
  marker; `generator.py` uses it for the "generated by generator.py" front
  matter stamp. Rename the incoming one `DESCRIPTION_MARKER` and leave
  `generator.py`'s alone, since it is written into every generated file and
  matched by `clean_generated()`.
- **`run()` folds into the existing subprocess style.** `generator.py` already
  calls `subprocess.run` directly; keep `run()` as the one helper that fails
  loudly for `gh`, and let the existing `clone()` keep its own `check=False`
  handling.
- **`check_icons()` is dropped.** It probed each icon URL with a `HEAD` request.
  The generator now downloads every image (step 3), so a missing one is
  discovered by the download itself and warned about there — one source of
  truth for "this application has no icon", instead of a probe that can
  disagree with what was fetched.
- **`check_repositories()` is kept**, and gains a second job: the generator
  already clones every application repo, so a repository that does not exist is
  a clone failure too. Keep the `gh api repos/<owner>/<repo>` probe with its
  three-valued result (exists / definite 404 / unknown, so an unauthenticated
  `gh` produces "could not check N repositories" rather than false "does not
  exist" warnings), and report a clone failure against the same entry rather
  than warning twice about the same application.
- **Everything is read through `gh`, not the anonymous raw host.** Found while
  implementing this: `raw.githubusercontent.com` rate-limits anonymous callers
  hard enough to fail a build outright — a few dozen requests returned `429 Too
  Many Requests`, and `index.py`'s "any non-404 is fatal" rule turned that into
  a dead build. Reading through `gh api repos/<repo>/contents/<path>` with an
  `Accept: application/vnd.github.raw` header serves the same bytes under the
  maintainer's 5000/hour credentials, which this script already depends on for
  the repository listing. Both the `_index.md` fetch and the image download go
  this way, each falling back to the raw URL if `gh` cannot answer at all. The
  `icon` field in the catalog is unaffected — it is rewritten to `/images/`
  regardless of how the bytes arrived.
- **The empty-catalog guard is kept and strengthened.** `index.py` refuses to
  write an index with no starters, so an API hiccup cannot blank the published
  list. Here it must additionally not *destroy* the previous build:
  `clean_generated()` deletes the existing `content/apps/` group directories, so
  the guard runs **before** any deletion, and the run exits non-zero with
  nothing touched.

The `--offline` flag stays and now covers the catalog too: with `--offline`,
`generator.py` skips the API entirely and reads the catalog written by the
previous run (step 2) instead. This is what makes a network-free rebuild
possible now that there is no committed `support/index.json` to fall back to.

### 2. `static/index.json` — the catalog, published from our domain

The merged generator writes the catalog to `static/index.json`, served at
`https://trustable.it/index.json`.

Same shape as `support/index.json` — `generated`, `starters`, `applications` —
with one difference: every `icon` is the **full URL** of the downloaded copy,
`https://trustable.it/images/<file>`, rather than a raw GitHub URL. An entry
whose image could not be fetched carries no `icon` at all, matching what the
generated pages do.

The catalog carries absolute URLs while the generated pages keep the
site-absolute `/images/<file>` path. The two differ because their readers do:
a page is served from this site, so a path resolves — and resolves under a local
`zola serve` preview too, which a hardcoded production URL would not. The
catalog is read by things that are *not* being served from here, and an entry
that does not say where its image lives is of no use to them. The domain is
`trustable.it`, matching `base_url` and `static/CNAME` — see spec/5-domain.md.

Reading the catalog back with `--offline` therefore meets icons that are
already ours. Those are stripped to the path the page wants rather than
re-downloaded, and the image they name is claimed so the pruning step does not
delete the very files the run is about to publish. An icon naming a file that
is no longer in `static/images/` is dropped with a warning, exactly as an image
that could not be fetched is.

`starters` is written through unchanged. Its `repo` and `templates` are GitHub
paths, not image URLs — they are where a user clones from, so they must keep
naming GitHub.

`generated` is stamped when the catalog is fetched, as `index.py` does today.
This file is committed, so `generated` alone changes on every run and the diff
is never empty; the run summary reports whether the starter and application
lists *actually* moved, reusing the content comparison `index.py` already does
(compare `starters` and `applications`, ignore `generated`).

With `--offline` this file is the input rather than the output: it is read back
in, its `/images/` icons are resolved against `static/images/`, and it is left
alone.

### 3. Download every image into `static/images/`

Every image the site shows is copied into the repository and served from our
own domain.

**Naming.** One file per source file, named after the repository it came from:

```
static/images/<owner>-<repo>.png
```

So `trustable-ai/minicrm`'s `screenshot.png` becomes
`static/images/trustable-ai-minicrm.png`, served at
`https://trustable.it/images/trustable-ai-minicrm.png`. The name derives from
owner and repository only, so an application listed under more than one group
resolves to one file, downloaded once.

A README may illustrate itself with a second image that is not the screenshot
(spec/12-readme.md was explicit about this). Those keep the file's own path in
the name, so they cannot collide with the screenshot or with each other:

```
static/images/<owner>-<repo>-<path>.<ext>
```

where `<path>` is the path within the repository, lowercased with every run of
non-alphanumeric characters collapsed to `-` (`docs/ui/detail.png` →
`docs-ui-detail`). `screenshot.png` at the repository root is the one special
case that drops the path, being the icon and by far the common one. The
extension is the source file's, so a `.jpg` or `.svg` in a README survives.

**Fetching.** `local_image()` takes either a raw GitHub URL or a
repository-relative path plus the repo it belongs to, and returns the
site-absolute `/images/<file>`:

- **Reuse the clone first.** Every application repo is already cloned into
  `.templates/<name>/` for its README, so the file is usually on disk already.
  Copy it from the checkout when the path resolves there, and fall back to an
  HTTP GET only when it does not. A normal build therefore does no extra
  network I/O, and `--offline` keeps working.
- Return `None` when the file cannot be had — not in the clone and not
  fetchable — and warn naming the repository and the path.
- A source that is absolute but *not* raw GitHub is left untouched: an image
  deliberately hosted elsewhere is not ours to copy.

**Consumers.**

- `write_group()` writes `local_image(app["icon"])` into `extra.icon`; on
  `None` the entry gets no `icon`, exactly as a catalog entry with no icon
  behaves today.
- `absolute_images()` currently rewrites relative README sources to a raw base
  URL. It now resolves them to the local copy instead — the relative path names
  a file in the repository, so it maps into `static/images/` directly, without
  going through a raw URL at all. Rename it `localize_images()`, since it no
  longer makes anything absolute.
- `drop_icon_image()` needs no change: it compares an image's source with the
  icon, and both sides are now the same `/images/<file>` path, so the comparison
  stays like-for-like. Its ordering comment in `write_group()` — "Absolute
  first, so the icon comparison is between like and like" — becomes "Localize
  first".

**Pruning.** Add `clean_images()`, run after generation, deleting any file in
`static/images/` that no application referenced this run — the `clean_icons()`
of spec/7-publish.md, restored for the same reason: without it an application
that leaves the catalog keeps its image published forever. `static/images/` is
wholly generator-owned; no hand-written file goes there, which is why it is a
new directory and not the existing `static/` root.

### 4. `build.sh` — one step, and the submodule leaves the build

- Drop the `uv run --no-project support/index.py` step. `generator.py` now does
  that work, and `uv` is no longer needed to supply an interpreter for it.
- `generator.py` keeps its `#!/usr/bin/env -S uv run --script` shebang and PEP
  723 block; it stays standard-library-only plus the `gh` CLI, so the block
  needs no dependencies added.
- `BUILD_PATHS` is `(content/apps docs)`; add `static/images` and
  `static/index.json`.
- Update the header comment and the commit message, both of which describe
  generating from `support/index.json`.
- **The `gh` dependency becomes the website's.** `build.sh` should fail early
  and clearly when `gh` is missing or unauthenticated, rather than deep inside
  the generator — this is a new requirement for anyone building the site, where
  before it came in through the submodule.
- **`--fast` skips the network.** `./build.sh [serve|build] --fast` runs
  `generator.py --offline`: the catalog is read back from `static/index.json`
  and the images already in `static/images/` are reused, so nothing is fetched
  and nothing is downloaded. Pages are still regenerated in full, so a template
  or generator change is picked up — only the GitHub round trip is skipped.
  The `gh` check is skipped with it, since this path needs neither the CLI nor
  the network; the full path's error message points at `--fast` as the way to
  rebuild without one. The flag is positional-independent (`build --fast` and
  `--fast build` both work).

  This is for iterating locally. A publishing build should be a full one, or the
  site is generated from whatever the organization looked like the last time
  someone ran it — which is the staleness the rest of this spec exists to
  prevent.

### 5. The `support` submodule

Building the site no longer reads it, so:

- `generator.py`'s `INDEX` constant, its "not checked out — run `git submodule
  update --init support`" error, and the spec/7-publish.md ordering constraint
  (catalog pushed before site) all go. That constraint existed because the
  published site described applications a not-yet-pushed catalog commit
  confirmed; with the catalog generated and committed here, there is nothing to
  order.
- **The submodule itself stays checked out.** `support/` also holds
  `support.sh`, `update.sh`, `profile/` and the rest of the support tooling,
  which this spec does not touch. Only the build's dependency on
  `support/index.json` is removed.
- Publishing the *upstream* catalog from `support/` remains a separate,
  deliberate act for Trustable's own discovery, unchanged and now decoupled
  from building the website.

### 6. Update the specs

- `spec/12-readme.md` — its section 2 ("Absolute screenshot URL, no local
  copy") is reversed here. Add a superseded note pointing to this spec rather
  than rewriting it, the way spec/7-publish.md marks its own superseded parts.
- `spec/7-publish.md` — its step 1 (`build.sh` runs `support/index.py`), its
  step 2 (`generator.py` reads `support/index.json`) and its "Publishing by
  hand" ordering constraint are superseded. Same treatment: a note at the top
  pointing here.
- `spec/4-generate.md` — rewrite for the merged generator: it now fetches the
  catalog itself, and its outputs include `static/index.json` and
  `static/images/<owner>-<repo>.png`.
- `spec/8-index.md` — it documents the catalog logic, which is now implemented
  in `generator.py`. Note that the website generates its own copy with this
  logic and publishes it at `https://trustable.it/index.json`, while
  `support/index.py` and its raw GitHub `index.json` remain what Trustable
  reads.

## Verification

- `./build.sh build` succeeds from a clean checkout with `support/` not
  initialised.
- `./generator.py --offline` succeeds with the network blocked, regenerating
  the same pages from the committed `static/index.json` and `static/images/`.
- `static/index.json` matches the catalog `support/index.py` produces for the
  same organisation state, entry for entry, apart from the rewritten `icon`
  fields — the ported logic is behaviour-preserving.
- Each downloaded image is a valid PNG and byte-identical to the one in the
  application's clone, so reading through `gh` does not corrupt the bytes.
- Two consecutive runs produce byte-identical pages.
- `grep -rn 'raw\.githubusercontent\.com' content/ static/index.json` returns
  nothing.
- Every `icon` in `static/index.json` is `https://trustable.it/images/<file>`
  and names a file present in `static/images/`, while every generated page's
  `extra.icon` is the bare `/images/<file>` path.
- Two consecutive `--offline` runs leave the icons unchanged — no doubled
  `https://trustable.it` prefix — and delete none of the images.
- `docs/index.json` and `docs/images/` exist after the build, so both are
  actually served.
- An application removed from the catalog loses its page and its file from
  `static/images/` on the next build.
- With the organisation returning no starters, the run exits non-zero and
  `content/apps/` is left untouched.
- The gallery and an application page render with the network blocked apart
  from the site's own origin.

## Out of scope

- **The page hero does not render, and did not before this change either.**
  `page.html` emits `extra.icon` as a `<img class="page-hero">` inside its
  `doc_content` block, and the generated pages carry the field, but no
  application page in `docs/` contains that tag — on this branch or on `main`,
  where the icon was still a raw GitHub URL. So the hero is broken independently
  of how the image is addressed, and fixing it is a separate change. The gallery
  tiles, which read the same field, do render and now use the local copies.
- Four untracked files under `content/documentation/` (`setup.md`, `config.md`,
  `edit.md`, `list.md`) have no TOML front matter and fail `zola build`. They
  are unrelated work in progress; the build above was verified with them
  temporarily set aside, and they were restored untouched.
- `support/index.py` itself, and the upstream `index.json` it publishes.
- Trustable's own discovery, which keeps reading the raw GitHub catalog.
- Any change to the page templates or to how README copy is selected.
